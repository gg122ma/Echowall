# Claude Interface Governance

> Planning only. Cross-reference `CLAUDE_PRODUCTION_ARCHITECTURE_REVIEW.md §2.2` for why "adapter-first" was chosen over direct-in-UI or a custom server.

## 1. Key finding: most of these interfaces already exist

Unlike a typical "add abstraction layers" exercise, verified source shows **five services already built as swappable provider objects**, each exposing a `ready()/list()/create()/subscribe()/useProvider()`-shaped surface specifically so a real backend can be dropped in without UI callers changing:

- `services/map-note-service.js` (`MapNoteService`)
- `services/study-submission-service.js` (`StudyUploadService`) — its own code comment states the intent verbatim: *"a future real backend (Supabase Storage, S3, Cloudinary) can be dropped in via `StudyUploadService.useProvider(...)` without any UI caller needing to change."*
- `services/moderation-service.js` (`ModerationService`)
- `services/admin-permission-service.js` (`AdminPermissionService`)
- `services/admin-audit-service.js` (`AdminAuditService`)

**Recommendation: extend this exact pattern to the remaining services rather than inventing a different abstraction style.** `app-data.js`'s `EchoNoteStore` (`createPlaceNote/listBuildingNotes/setPlaceNoteHidden/deletePlaceNote/restorePlaceNote/subscribe`) is already close to this shape and should gain a `useProvider()` seam the same way. `comment-service.js`, `community-service.js`, and `permission-service.js` are thinner and can be swapped by editing their internals directly (small enough that a formal provider-swap seam would be over-engineering for what they do).

## 3. When to use which access path (decision rule, concrete not abstract)

- **Direct Data API + RLS**: any read, and any write where "row belongs to me" is the entire authorization rule (profile update, own-comment... though comment edit doesn't exist yet — see data doc).
- **Postgres RPC (`SECURITY INVOKER` unless stated otherwise)**: any write with cross-row logic that can't be expressed as a row predicate — voting (touches both `note_votes` and a `posts.score` cache), moderation transitions (touches `moderation_items` + the content's own visibility flag + `audit_actions` in one transaction), role grants (`user_roles` + `audit_actions`).
- **Edge Function**: anything that must hold a *secret* (Cloudinary signing/deletion) or must call an external HTTP API not reachable safely from the browser context.
- **Direct Cloudinary browser upload**: always, once signed — never proxy the actual image bytes through Supabase.

Every `SECURITY DEFINER` function used above (role grants, audit writes if a definer context is needed for the append-only guarantee) must pin `SET search_path = ''` and fully qualify object names — this is not a stylistic note, it's the current, real Postgres/Supabase guidance against privilege-escalation via search-path shadowing (see `CLAUDE_DATA_AUTH_RLS_REVIEW.md §2`).

## 4. Multi-system failure design

| Scenario | Current prototype behavior | Production design |
|---|---|---|
| Cloudinary upload succeeds, post insert fails | Not handled today beyond "note removed from in-memory array" — no asset cleanup, confirmed orphan risk in the July doc, still true | Call `cloudinary-delete` immediately (idempotent); on double failure, leave `media_assets` row `pending-orphan` for scheduled sweep |
| Post insert succeeds, media row fails | N/A today (single LocalStorage write) | Wrap post + media metadata write in one RPC/transaction so this can't happen; if it somehow does, reconcile on next load rather than silently losing the image reference |
| User double-clicks Publish | No protection — a second click can create a second identical note | **New requirement**: client generates a UUID draft/idempotency key per compose session; the create RPC upserts on that key so a retried/duplicated request is a no-op the second time |
| Response is lost after server success | No equivalent today (synchronous local write can't "lose" a response) | Client re-fetches/reconciles from the database rather than assuming failure and resubmitting; combined with the idempotency key above, a resubmit is safe even if reconciliation is skipped |
| Comment is duplicated | Currently possible (no idempotency check in `createComment()`) | Same idempotency-key pattern as posts |
| Vote race (rapid double-click) | Currently client-side toggle, resolves fine in a single browser tab but has no cross-tab/cross-request atomicity | Atomic upsert RPC (§2) — resolves deterministically under concurrent calls from the same user |
| Session refresh during upload | N/A today (session never expires) | Await auth readiness before submit; on mid-flight refresh failure, surface a clear re-auth prompt, do not silently drop the compose draft (keep it client-side until confirmed submitted) |
| Study object succeeds but submission row fails | N/A today (both live in the same IndexedDB transaction) | Same transactional-write requirement as posts+media; use the file's SHA-256 as a natural idempotency anchor — a retried upload of the same bytes is recognized, not duplicated (mirrors the existing client-side dedup, just moved server-side) |
| Approved metadata references missing object | N/A today | Approval RPC should verify the Storage object exists before flipping `moderation_status` to `approved`; if missing, fail the approval with a clear operator-facing error rather than publishing a broken link |
| Cloudinary signature expires (1-hour window, confirmed via current Cloudinary docs) | N/A today (no real signing yet) | Client should request a fresh signature if upload hasn't started within a safety margin (e.g. 5 minutes) rather than attempting a stale signature and surfacing Cloudinary's generic auth error |

**Optimistic vs. pessimistic UI:** keep the current optimistic-insert-with-rollback pattern already used by `EchoNoteStore.createPlaceNote()` (insert → persist → roll back on failure) — it's a good pattern and matches user expectations already trained by the prototype. Production's async round-trip just makes the rollback path a real possibility instead of a near-never edge case, so it needs an actual error toast (already present in the UI) rather than being purely defensive dead code.

## 6. Ask Echo — architectural risk flagged for the security review

Confirmed via source: `free-ai-adapter.js` reads `EchoConfig.freeAI.openRouterToken` and sends it as `Authorization: Bearer ${token}` directly from the browser to `openrouter.ai`; `bisheng-adapter.js` does the same pattern with `config.publicToken`. **Today both fields are empty — no live secret exists in the repository.** But the *pattern* is not secret-safe: if either field is ever filled in inside the public `config/app-config.js`, it ships to every visitor's browser. **Recommendation, if either remote AI tier is ever activated in production:** route it through a Supabase Edge Function proxy (same shape as the Cloudinary signing function) so the real token never reaches frontend config, rather than assuming a "publicToken" name implies it's safe to expose. This is a design recommendation to carry forward if/when Ask Echo's remote tiers are turned on — not an immediate fix, since nothing is currently exposed, but a decision to record so it isn't accidentally introduced later. See `CLAUDE_ARCHITECTURE_DECISIONS.md`.
